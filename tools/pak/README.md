# tools/pak — pak, locres and cooked-asset tooling (Tests #1 and #2, 2026-09-13)

Pure-Python (stdlib only) plus a tiny Rust CLI for Oodle decompression. All scripts import each other from this folder; run them from anywhere.

| File | What it does |
|---|---|
| `paklib.py` | Reads Unreal `.pak` **version 11, unencrypted** files (footer, primary index, path-hash index, full directory index, encoded entries) and writes new uncompressed v11 paks. Validated against the game's own paks: all path hashes reproduced exactly. |
| `scanpaks.py <needle> [paks…]` | Lists every pak's mount point and file count, prints files matching `<needle>`, and dumps each pak's file list to `pakindex/<pak>.txt`. Used to build `reference/pak-contents-map.md`. |
| `locres.py` | Parses/serializes Unreal `.locres` v3 string tables with a byte-exact round trip. |
| `oozcli/` | Rust CLI over the `oozextract` crate (open-source Oodle decoder). `cargo build --release` → `oozcli <in> <uncompressed_size> <out>`. Needed because pak entries are Oodle-compressed. Multi-block entries: decompress each block to `block_size` bytes and concatenate (see `build_test_pak.py` / the extraction snippet in `research/2026-09-13-test2-datatable-override.md`). |
| `uasset.py <file.uasset>` | Reads a cooked UE5 package header: summary, name table, and the summary ints (export/import offsets). Prints whether the package uses unversioned properties (Bodycam: yes). |
| `udstruct.py <S.uasset> <S.uexp>` | Decodes a cooked **UserDefinedStruct** export → ordered property schema (type, name, size, enum/struct/class refs). This is how row layouts are learned without the editor or a .usmap. |

## Cooked-asset facts learned (Bodycam, UE 5.5)
- Packages are **unversioned** (`PackageFlags & 0x2000`): no property tags in export data; a struct value = uint16 fragment header(s) [+ zero-mask] + values in declared order. Fragment bits: `SkipNum = v & 0x7f`, `HasZeros = v & 0x80`, `IsLast = v & 0x100`, `ValueNum = v >> 9`.
- FName in export data = int32 name index + int32 number (`number-1` is the `_N` suffix; 0 = no suffix).
- FText = uint32 flags + int8 history: `11` StringTable (FName table id + FString key), `0` Base (FString ns, key, source; empty ns written as a 1-byte NUL string), `-1` None (int32 has-string + optional FString).
- Enum bytes in unversioned data are raw bytes, not names. Bool = 1 byte. Object refs = int32 package index (negative = import). Soft object path = 2 FNames + FString sub-path. GameplayTagContainer = int32 count + FNames. GameplayTag = nested unversioned struct (header + FName).
- `.uexp` = export data + 4-byte tag `C1 83 2A 9E`. Export `SerialSize` lives in the `.uasset` export table; `BulkDataStartOffset` in the summary = header size + SerialSize. Both must be patched when export data changes size.
- Adding a row without touching the name table: reuse an existing FName index with a new Number.
- Zero-valued fields (0, false, empty) are **not stored** in unversioned data — the fragment header's zero-mask marks them absent. Never pattern-match for a `00` byte; use recorded field offsets.
- `FLinearColor` is native-serialized (16 raw bytes, no nested header). `FGameplayTag` is a nested unversioned struct (header + FName). `FGameplayTagContainer` is int32 count + FNames.
- FName comparison is case-insensitive: the UI table's `DeathMatch` and `DT_GamemodeInfo`'s `Deathmatch` are the same key.
- Name-table entries carry two uint16 hashes: CasePreservingHash = `crc32(utf-32-le bytes) & 0xffff` (reproduced exactly); NonCasePreservingHash is a legacy table hash (best-effort). The loader discards both on read.
- Cooked package header order: summary → names → imports (32 B each) → exports (96 B each) → depends → asset-registry block → preload deps (int32 package indices). Export `serial_offset` = header size for the first export; `BulkDataStartOffset` = header + last export end.
- Import pattern for a `/Game` asset: one `Package` import (class `/Script/CoreUObject.Package`, outer 0, name = package path) plus one object import (class = the asset's class, outer = the package import, name = asset name). Object imports referenced by export data appear in the export's **CreateBeforeSerialization** preload group.
- Level packages (`.umap`) carry a **data-resource table** after the preload deps (`DataResourceOffset`): version + count + 45-byte entries whose `SerialOffset` is relative to the owning export, so header edits don't disturb it. WorldSettings unversioned layout (Bodycam's AWorldSettings schema): property #22 = `NavigationSystemConfigOverride`, **#33 = `DefaultGameMode`**, #58 = a trailing struct; stock DM/TDM variants store #22 and #58 only (`16 02 | 23 03`), Wingman stores #33 too (`16 02 | 0a 02 | 18 03`).
- Cooked DataTable `.uexp`: `00 03` + RowStruct import + 4 zero bytes + int32 row count + rows (FName key + unversioned struct value) + tag. `BP_MapDefinition` rows are 15 bytes (`00 05`, IsActive byte, Metadata ref).
- Blueprint host flow: see `kismet.py` and `research/2026-09-14-host-flow-decoded.md`.
- The file bridge (`device_commit_files`) may reuse a cached upload when the staged file name repeats — give each pak version a unique staged name.

## Notes
- The game's paks: version 11, mount point `../../../`, Oodle compression, no encryption on assets, no signing. Only `Bodycam/Config/*.ini` entries are encrypted.
- A mod pak goes in `<Bodycam>\Bodycam\Content\Paks\~mods\` and ends in `_P.pak`. Paks mount at game start only — relaunch after changing them.
- We write **uncompressed** entries by default (no Oodle compressor needed; the game reads them fine). `write_pak(..., compress=[rel, ...])` stores the listed entries as **Zlib** blocks (1 MB, method name `Zlib` in the footer, block sizes in the encoded index, relative block offsets in the data header) — first used for the 68 MB `AssetRegistry.bin` override. For big content paks `repak` (github.com/trumank/repak) or UnrealPak from UE 5.5 on Sam's PC remain options.
- GitHub is blocked from the Cowork cloud sandbox; crates.io is not — hence `oozcli`.
- Keep every extracted game file local; never commit them (see `instructions.md` §4.2).
